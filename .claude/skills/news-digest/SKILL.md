# news-digest

ユーザーの関心プロフィール（`profile.md`）に沿ってニュースを集め、話題ごとに独自の記事として書き起こした日次ダイジェストを作る。集めた記事は本文の材料であり、ダイジェストの中では出典として示す。
手順は以下のとおり固定とし、関心の中身はすべて `profile.md` から読む。このスキル側でトピックを決め打ちしない。

パスはすべてリポジトリのルートからの相対パス。日付は日本時間（`TZ=Asia/Tokyo date +%F`）で扱う。

## 0. 実行できるリポジトリか確認する

`profile.md` が無い場合は、雛形リポジトリか初期設定前の複製リポジトリである。「README の手順で複製リポジトリを作り、`profile.md` を用意してください」と報告して終了する。

## 1. 読み込み

- `profile.md` を読む。見出しの意味は次のとおり。本文は自然文なので、意図を汲んで解釈する。HTML コメント（`<!-- -->`）の中は書き方の例なので、指定として扱わない。
  - `## 常に追う` — 毎回しっかり追う
  - `## 試しに追う` — 軽めに追う
  - `## 休止中` — 普段は追わない。大きな動きがあったときだけ拾う
  - `## 興味なし` — 除外する
  - `## 曜日ごとの調整` — 曜日や日の種類ごとの、上の区分への差分（下の「曜日ごとの調整」を参照）。無い・空・今日に当てはまる項目が無い場合は何も変えない
  - `## 読み方の好み` — 言語、件数、ソースの好みなど。ここに書かれた指定は以下の既定値より優先する
  - `## 表示機能` — ダイジェストに決まった形式の欄を足す機能の on / off（「表示機能」を参照）。関心のトピックではないので、収集の対象にしない
- `state/seen.jsonl` を読む（無ければ空とみなす）。1行1件で `{"date":"YYYY-MM-DD","url":"...","title":"..."}` の形式。
- `digests/` の中で最新のダイジェストのファイル名から前回の日付を得る。集める期間は前回の日付から今日まで。前回が無い場合は直近7日間とする。
- `state/profile-snapshot.md`（前回実行時の profile.md の写し）を読み、今の `profile.md` と比べる（`表示機能` は比べない）。`常に追う` と `試しに追う` に新しく加わったトピック（`休止中` から戻ったものを含む）は、前回の日付にかかわらず直近7日間を集める。言い回しを変えただけで関心の中身が同じものは、新しいトピックとみなさない。写しが無い場合は、すべてのトピックを新しいトピックとして扱う。
- 新しいトピックとして期間を広げた場合は、出力の対象期間の行にそのことを書き添える（例：`対象期間: 2026-10-26 〜 2026-10-27（新しく加わったトピックは 2026-10-20 から）`）。
- 今日のダイジェストが既にある場合は、上書きせずにそのことを報告して終了する。

**曜日ごとの調整**

- 今日の日の種類を決める。曜日は `TZ=Asia/Tokyo date +%u` で得る。**休日**は土日・国民の祝日（振替休日を含む）・東証の休場日（12/31〜1/3）、**平日**は休日以外。祝日かどうか確信が持てなければ WebSearch で確かめる。
- 項目は「曜日（月〜日）」「平日」「休日」のどれかに当てはまるものとして読む（「土日」「月〜金」のような書き方も意図を汲む）。今日に当てはまる項目だけを、上の区分への差分として適用する。書けることは次のとおり。
  - 区分の読み替え：トピックをその日だけ格上げ・格下げする（例：休止中 → 試しに追う、試しに追う → 常に追う、常に追う → 軽め）
  - 重み：トピック間の配分や詳しさを変える
  - 件数：その日の話題の数。`読み方の好み` の件数より優先する
  - その日だけのトピック：上の区分に無い話題を足す（例：来週の予定、週間まとめ）
- 複数の項目が当てはまる場合（例：祝日の月曜に「休日」と「月」）は両方適用し、矛盾する部分は「休日」の項目を優先する。
- `興味なし` は調整で覆さない。
- 調整で今日だけ追う、または今日だけ格上げされるトピックは、暦の上で直前にその項目が当てはまった日（最大7日前）から集める。基本の区分で追っている部分は、これまでどおり前回の日付から集める。
- `曜日ごとの調整` の変更は、スナップショットとの比較で新しいトピックとして扱わない。
- 以下の手順は、調整を適用した後の区分・件数・配分で行う。

## 2. 収集

WebSearch と WebFetch を使う。区分ごとに手厚さを変える。

- **常に追う**：トピックごとに2〜4本のクエリを投げる。英語と日本語の両方で検索する。プロフィールに一次ソースが挙がっていればそれも直接確認する。
- **試しに追う**：トピックごとに1〜2本のクエリ。
- **休止中**：トピックごとに1本のクエリを投げ、大きな発表や急な盛り上がりがあるかだけを見る。無ければ何も拾わない。

公開日が集める期間の外にある記事は捨てる。日付が分からない記事は、明らかに新しいものに限って採用する。

## 3. 話題にまとめる

- `seen.jsonl` にある URL は除く。ただし続報が出ている場合は、新しい記事を材料に続報として扱ってよい。
- `興味なし` に当たる話題とソースは除く。
- 同じ出来事や、互いに関係する出来事を扱う記事を1つの**話題**にまとめる。1つの話題には1〜4本のソースを使い、一次ソースがあれば必ず含める。
- 関連度（プロフィールとの近さ）と重要度（新規性・影響の大きさ）で話題に順位を付ける。
- 話題の数は **5〜8本**（`読み方の好み` に件数の指定があればそれを話題の数とみなす）。セレンディピティ枠を含む。同じトピックに偏りすぎないようにする。
- 材料が少ない日は、無理に話題を増やさない。

## 4. セレンディピティ枠

「常に追う」の話題に隣接するが、プロフィールのどこにも書かれていない話題を1つ選ぶ。

## 5. 表示機能

記事とは別に、決まった形式の欄（天気の表など）をダイジェストの冒頭に足す機能。既定ではすべて無効で、`profile.md` の `## 表示機能` で on にしたものだけを実行する。

- 各行は `- <機能名>: on|off（設定）` の形式。`on` 以外の値、行が無い機能、節そのものが無い場合は無効とする。
- 機能ごとの仕様は `.claude/skills/news-digest/features/` にある。機能名との対応は次のとおり。ここに無い機能名は無視し、最後の報告でそのことを伝える。

| 機能名 | 仕様 |
|---|---|
| `天気` | `features/weather.md` |

- 有効な機能の仕様を読み、その手順に従って HTML の断片（`<section class="feature …">`）を得る。断片は機能のスクリプトが出力したものを手を加えずに使う（数字や表を自分で書き直さない）。
- 機能の失敗はダイジェスト全体の失敗にしない。仕様に書かれたとおりに扱い、最後の報告で伝える。

## 6. 出力

`.claude/skills/news-digest/digest-template.html` をそのまま土台にして、`digests/YYYY/MM/YYYY-MM-DD.html` を書く（ディレクトリが無ければ作る）。

**構成**
- `<head>` と `<style>` は雛形から変えない。雛形内のコメントは出力に残さない。
- 表示機能の断片：`<header>` と `今日の要点` の間に、`profile.md` に書かれた順で置く。有効な機能が無ければ何も置かない。
- `今日の要点`：各話題を一文にまとめた箇条書き。各行はその話題の `article`（`#t1`, `#t2`, …）へのページ内リンクにする。
- 話題1つにつき `<article id="tN">` を1つ。重要度の順に並べ、セレンディピティ枠は最後に `class="serendipity"` を付けて置く。
- 各 `article` の中身：
  - `.kicker`：profile.md 上のトピック名
  - `<h2>`：その話題に自分で付けた見出し（ソースの見出しをそのまま使わない）
  - 本文の段落：通常は2〜4段落。profile.md で「詳細に」と指定された話題は厚めに、試しに追う話題やセレンディピティ枠は1段落でよい
  - `<ol class="sources" start="N">`：その話題で使ったソースの一覧。各 `<li id="sN">` にリンク付きの原題と、`.pub` に媒体名と公開日を書く

**本文の書き方**
- ソースを要約して並べるのではなく、複数のソースを突き合わせて、何が起きたか・背景・意味を自分の言葉で一つの記事に組み立てる。
- 事実を述べた文には、末尾に `<a class="cite" href="#sN">[N]</a>` で出典番号を付ける。番号は文書全体の通し番号にする。
- ソースに書かれていない推測や評価は、「見立て：」と明示したうえでのみ書く。数字は出典どおりに書く。
- ソースの文章を長く引き写さない。引用が必要なら短い一節を「」で示し、1つの話題につき1か所までにする。
- 本文は `読み方の好み` の言語で書く（既定は日本語）。ソースのタイトルは原題のままにする。
- テキストに含まれる `&` `<` `>` `"` はエスケープする。外部の JavaScript や画像は読み込まない。
- プロフィールの見直し提案は書かない。
- `曜日ごとの調整` を適用したこと（曜日・休日の判定、格上げや件数の変更）には、本文でも要点でも issue でも触れない。出力の形は調整の有無で変えない。その日だけのトピックの `.kicker` は、調整に書かれたトピック名にする。

## 7. 記録とコミット

1. 出典として使った記事をすべて `state/seen.jsonl` に追記する。
2. `seen.jsonl` から日付が30日より古い行を削除する。
3. 今の `profile.md` を `state/profile-snapshot.md` に上書きコピーする（次回の比較に使う）。
4. コミットして `origin` の `main` に直接プッシュする。今いるブランチが `main` 以外（クラウド実行で作られる `claude/` ブランチなど）でも、新しいブランチは作らず PR も出さない。`template` remote にはプッシュしない。

```bash
git add digests state
git commit -m "digest: YYYY-MM-DD"
git pull --rebase origin main
git push origin HEAD:main
```

`git pull --rebase` で衝突した場合は、`git rebase --abort` で元に戻し、衝突したファイルを報告して終了する。

`git add` が「ignored」で失敗した場合は、雛形リポジトリか初期設定（`.gitignore` の利用者データのブロックの削除）が済んでいない。`-f` は使わず、そのことを報告して終了する。
プッシュが拒否された場合は、エラー内容をそのまま報告する。force push はしない。

## 8. issue で知らせる

コミットとプッシュが済んだら、その日のダイジェストを issue にして、HTML を issue の artifact として添付する。GitHub 上（スマホを含む）で読めるようにするため。通知は `digest-notify` ワークフローが送る（本人名義の issue は本人に通知されないため）。

- GitHub の操作は `.claude/skills/news-digest/create-issue.sh` で行う。`gh api` を直接呼ばない（環境によっては承認待ちになり、無人実行が止まる。このスクリプトの実行は `.claude/settings.json` で許可されている）。`gh issue create` や `gh issue artifact` などの `gh issue` 系のコマンドも使わない（クラウド実行では GraphQL が使えず 403 になる。スクリプトは REST API を使う）。
- issue の本文は、Write ツールで `.tmp/digest-issue-body.md` に書く（`.gitignore` で無視されている。スクリプトが使い終わったら削除する）。`mktemp` は使わない。
- 本文を書いたら、次のコマンドを**そのまま単独で**実行する。`cd` や変数代入、`&&`、パイプなどと組み合わせると許可設定に一致せず、承認待ちになる。

```bash
bash .claude/skills/news-digest/create-issue.sh YYYY-MM-DD
```

スクリプトはラベル `digest` を（無ければ）作り、issue「digest: YYYY-MM-DD」を立て、`digests/YYYY/MM/YYYY-MM-DD.html` を artifact として添付して、issue の URL を出力する。終了コードは 0（成功）、1（issue を作れなかった）、2（issue は作れたが artifact を作れなかった）。

**issue の本文**（Markdown）
- 1行目に対象期間（HTML の対象期間の行と同じ内容）
- 有効な表示機能があれば、仕様の「issue の本文」に従った行を続ける（仕様にその項が無い機能は何も書かない）
- `## 今日の要点` に、HTML の要点と同じ箇条書き
- コミットしたファイルへのリンク：`https://github.com/$R/blob/main/digests/YYYY/MM/YYYY-MM-DD.html`
- 末尾に「全文はこの issue の Artifacts から Preview で読めます。」と書く

**失敗したとき**
- ダイジェストは手順7でコミット済みなので、この手順で失敗しても実行全体は失敗にしない。
- issue を作れなかった場合（終了コード 1）は、エラー内容を報告して終了する。
- artifact を作れなかった場合（終了コード 2）は、issue はそのまま残し（要点とファイルへのリンクは読める）、issue の URL とエラー内容を報告する。
- やり直しは繰り返さない。issue は close しない（読んだらユーザーが close する）。

最後に、作成したファイルのパス、話題の数・出典の数、issue の URL を1〜2行で報告する。
